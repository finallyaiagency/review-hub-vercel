Agent Looping — The Core Loop

Week 1: Build an Agent
Slide 1 of 4

The Agent Loop

The core loop: Perceive → Reason → Act → Observe → Repeat

Unlike a single LLM call, an agent:

• Runs autonomously without hand-holding

• Iterates until the task is complete

• Doesn't need perfect prompting — it recovers

• Handles multi-step, multi-tool workflows

Slide 2 of 4

Prompt vs Agent

A prompt is a one-shot Q&A. An agent is a multi-step task engine.

PromptAgent
One-shot Q&AMulti-step task
Needs perfect inputRecovers from bad input
No memoryMaintains state
Single model callTool-calling loop
Slide 3 of 4

The Loop in Practice

1. Perceive: Receive task + current state

2. Reason: Decide what to do next

3. Act: Call a tool or generate output

4. Observe: See what happened

5. Repeat: Until task is done or max steps hit


Key: The agent decides when to stop, not the user.

Slide 4 of 4

Why This Matters for FDEs

Clients don't need another chatbot. They need autonomous systems that:

• Process invoices while you sleep

• Handle 1,000 support tickets without fatigue

• Route leads 24/7 without supervision


The agent loop is the engine of every FDE deployment.

Tool Usage — Giving Your Agent Hands

Week 1: Build an Agent
Slide 1 of 4

Why Tools?

An LLM alone can only generate text. To do real work, an agent needs:

🔧 APIs — Read/write external systems

🔧 Databases — Query and store data

🔧 File System — Read/write documents

🔧 Web Search — Fetch real-time info

🔧 Email — Send notifications


Tools = the agent's hands

Slide 2 of 4

Tool Schema

Every tool needs a defined schema:

{
  "name": "search_crm",
  "description": "Search CRM for contact",
  "parameters": {
    "email": {"type": "string"},
    "limit": {"type": "integer", "default": 5}
  }
}

The model reads the schema and decides when to call it.

Slide 3 of 4

Tool Registry Pattern

Tool Registry = a list of all available tools with their schemas.

1. Agent receives task

2. Model looks at tool registry

3. Model decides which tool(s) to call

4. System executes the tool

5. Result goes back into the loop


No hardcoded logic — the model routes dynamically.

Slide 4 of 4

3 Tools for an Invoice Agent

1. search_vendor — Look up vendor by name/ID in ERP

2. extract_invoice_data — Parse invoice PDF for amount, date, PO#

3. match_po — Compare invoice line items against purchase order


Each has a clear name, description, and parameter schema.

Guardrails — Keeping Your Agent Safe

Week 1: Build an Agent
Slide 1 of 4

Why Guardrails?

Without guardrails, your agent can:

❌ Hallucinate fake data into a client's CRM

❌ Leak PII (names, emails, financial data)

❌ Call expensive APIs in infinite loops

❌ Take destructive actions (delete, overwrite)


Guardrails transform a liability into a tool.

Slide 2 of 4

3 Essential Guardrails

1. Output Validation — Reject malformed JSON, check field types, enforce ranges

2. Content Filtering — Block PII, profanity, sensitive data from leaving the system

3. Human-in-the-Loop — Require approval for destructive actions (deletes, large payments, external sends)

Slide 3 of 4

Rate Limiting & Budgets

Agents can burn money fast if unchecked:

• Per-call cost cap: Max $0.50 per agent run

• Per-minute rate limit: 60 API calls/min

• Daily budget: $10/day per client

• Circuit breaker: Kill the agent if it enters a loop


These prevent runaway costs.

Slide 4 of 4

Guardrail Architecture

Input → Guardrail → Agent → Guardrail → Output
       ↑                        ↓
  Content Filter          Validation Check
       ↑                        ↓
  Blocked? → Reject        Failed? → Retry/Human

Guardrails at both entry and exit points.

Slide 2 of 4

Short-Term Memory in Practice

The agent's context window contains:

• System prompt (instructions, rules)

• Conversation history (last N turns)

• Current task state

• Tool call results


Challenge: Context windows fill up. Strategy: Summarize older turns.

Slide 3 of 4

Long-Term Memory with RAG

RAG = Retrieval Augmented Generation

1. Store past sessions as embeddings in a vector DB

2. When a new task arrives, retrieve relevant history

3. Inject it into the context window

4. Agent acts with full context


Example: An invoice agent remembers 'This vendor always sends late invoices'

Slide 4 of 4

Invoice Agent Memory Example

Across sessions, remembers:

• Vendor payment terms

• Preferred invoice formats

• Common discrepancy patterns

• Historical approval times


Current session, tracks:

• Which invoice is being processed

• What steps have been completed

• What data has been extracted

• What errors occurred

Audit Trail — Show Your Work

Week 1: Build an Agent
Slide 1 of 4

Why Audit Trails?

Clients fear the black box:

❌ 'What did the agent do?'

❌ 'Why did it make that decision?'

❌ 'Can we prove it followed the rules?'


Audit trails answer:

✅ Every step is logged

✅ Every decision is explainable

✅ Every action is verifiable

Slide 2 of 4

What to Log

Every agent step must log:

1. Timestamp — When did it happen?

2. Input — What was the agent told?

3. Reasoning — Why did it choose this action?

4. Tool Call — What tool, with what params?

5. Result — What did the tool return?

6. Decision — What did the agent decide next?

Slide 3 of 4

Audit Trail Format

{
  "step": 3,
  "timestamp": "2026-07-21T10:32:15Z",
  "input": "Match invoice INV-442 to PO-889",
  "reasoning": "Need to look up PO details",
  "tool": "search_purchase_order",
  "params": {"po_id": "PO-889"},
  "result": {"status": "found", "total": 15000},
  "next": "compare_line_items"
}

Every step is a JSON record.

Slide 4 of 4

Glass Box, Not Black Box

With a full audit trail, you can:

• Replay the agent's entire decision process

• Debug failures by examining each step

• Prove compliance to auditors

• Build client trust by showing exactly what happened


This is your competitive advantage as an FDE.

Defined JSON Schema — No Free-Form Text

Week 2: Make It Recoverable
Slide 1 of 4

Why JSON Schemas?

Free-form text is fragile:

❌ Model can change format anytime

❌ Parsing breaks silently

❌ No validation — garbage in, garbage out

❌ Impossible to guarantee structure


JSON schemas fix this:

✅ Predictable structure

✅ Automatic validation

✅ Clear error messages

✅ Works with any model

Slide 2 of 4

JSON Schema Example

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["invoice_id", "action"],
  "properties": {
    "invoice_id": {"type": "string", "pattern": "^INV-\\d+$"},
    "action": {"type": "string", "enum": ["approve", "reject", "flag"]},
    "amount": {"type": "number", "minimum": 0}
  }
}

Every field has a type, format, and constraints.

Slide 3 of 4

Schema Benefits

1. Validation — Reject bad output immediately

2. Documentation — Schema IS the contract

3. Type Safety — Strings stay strings, numbers stay numbers

4. Tooling — IDEs, CI/CD, and tests can validate automatically

5. Versioning — Track schema changes over time


No schema = no production.

Slide 4 of 4

Your Tool Schemas

Every tool in your agent needs:

1. Name — snake_case, unique

2. Description — What does it do? When should the agent call it?

3. Parameters — JSON Schema for each parameter

4. Returns — What shape does the result have?


Go through your Week 1 tools and add schemas.

Schema Validation — Reject Bad Output

Week 2: Make It Recoverable
Slide 1 of 4

The Validation Gate

Model Output → Parse JSON → Validate Schema → Pass → Continue
                               ↓ Fail
                    Log Error → Retry (max 3) → Fail → Escalate to Human

Validation is a non-negotiable gate. Nothing passes without it.

Slide 2 of 4

What Can Go Wrong?

Common validation failures:

1. Malformed JSON — Missing bracket, trailing comma

2. Missing fields — Required field is null

3. Wrong types — String where number expected

4. Out of range — Amount is negative

5. Invalid enum — 'aprove' instead of 'approve'


Each needs a different recovery strategy.

Slide 3 of 4

Retry Strategy

When validation fails:

1. Retry 1 — 'Output failed validation. Correct and try again.'

2. Retry 2 — 'Still invalid. Show the exact error.'

3. Retry 3 — 'Use the fallback template.'

4. Escalate — 'Validation failed after 3 retries. Flagging for human review.'


Never retry forever. Set a budget.

Slide 4 of 4

Validation in Practice

from jsonschema import validate, ValidationError

def safe_model_call(prompt, schema, max_retries=3):
    for attempt in range(max_retries):
        raw = model.generate(prompt)
        try:
            parsed = json.loads(raw)
            validate(instance=parsed, schema=schema)
            return parsed
        except (json.JSONDecodeError, ValidationError) as e:
            log_error(f"Attempt {attempt+1} failed: {e}")
            prompt += f"\nError: {e}. Fix and retry."
    escalate_to_human(raw)

Slide 2 of 4

The Recovery Hierarchy

Best:  Agent handles it automatically
Good:  Agent flags it with a clear message
Okay:  Agent routes to the right human
Worst: Agent fails silently (data corruption, double payment)

Design for the best. Always avoid the worst.

Slide 3 of 4

Exception Handling Patterns

1. Retry — Transient failure (timeout, rate limit)

2. Fallback — Alternative model, tool, or data source

3. Skip — Optional step, can proceed without it

4. Flag — Document and continue, human reviews later

5. Halt — Stop processing, escalate immediately


Choose the right pattern for each failure mode.

Week 2 · Day 13 of 30

Failure Handling Architecture

Week 2: Make It Recoverable
Slide 1 of 4

System-Level Failures

Individual exceptions are handled per-step. System-level failures affect the entire agent:

🔴 Downstream API is down

🔴 Rate limit hit across all clients

🔴 Model provider outage

🔴 Database connection lost

🔴 Memory leak / context overflow


These need architectural solutions, not per-step fixes.

Slide 2 of 4

Circuit Breaker Pattern

Normal → Detecting failures → Open circuit → Timeout → Half-open → Try → Normal
                                                                    ↓ Fail
                                                              Open circuit (again)

After N consecutive failures, 'open' the circuit: stop calling, return fallback, alert.

After a timeout, try one request. If it succeeds, close the circuit. If it fails, stay open.

Slide 3 of 4

Backpressure & Queuing

When the system can't keep up:

1. Queue — Put requests in a FIFO queue

2. Backpressure — Signal upstream to slow down

3. Prioritize — Critical requests first

4. Drop — Non-critical requests after queue full


Better to queue than crash.

Slide 4 of 4

Graceful Degradation

When something fails, the system should degrade, not die:

• Model down → Switch to fallback model

• Database down → Use cached data

• Tool down → Skip that step, flag for later

• Context full → Summarize and continue


Degrade = still useful. Crash = useless.

Retry Logic — Exponential Backoff & Fallback

Week 3: Make It Measurable
Slide 1 of 4

Why Retry Logic?

Failures are inevitable. Retry logic is how you handle them:

• Transient failures — Timeout, rate limit, network blip (retry)

• Permanent failures — Bad input, auth error (don't retry)

• Degradation — Model is slow, use a faster one (fallback)


Knowing the difference is critical.

Slide 2 of 4

Exponential Backoff

Attempt 1: Wait 1s
Attempt 2: Wait 2s
Attempt 3: Wait 4s
Attempt 4: Wait 8s
Attempt 5: Wait 16s → Max reached, escalate

Formula: wait = base * (2 ^ attempt) + jitter

Jitter adds randomness so all clients don't retry simultaneously.

Slide 3 of 4

Fallback Chain

Primary:    GPT-4o → Expensive, accurate
Fallback 1: Claude Sonnet → Cheaper, still good
Fallback 2: Gemini Flash → Fast, cheap
Fallback 3: Rule-based → No model, just logic
Fallback 4: Human → Escalate

Each fallback is cheaper and less capable, but better than failing.

Slide 4 of 4

Retry Budget

Define limits before they hit your wallet:

• Max retries per step: 3

• Max total retries per run: 10

• Max time per run: 5 minutes

• Max cost per run: $0.50

• Fallback after: 3rd retry failure


When budget is exceeded → halt, log, alert.

🎙 Exercise

Record your retry strategy. How many retries? What backoff? When do you switch to a fallback model? When do you escalate to a human?

📇 Flashcards (5)

What's the difference between transient and permanent failures?
Transient = retry. Permanent = don't retry.
What is exponential backoff?
Wait time doubles each attempt: 1s, 2s, 4s, 8s, 16s
What is jitter?
Randomness added to backoff so clients don't retry simultaneously
Name the fallback chain order
Primary → Fallback 1 → Fallback 2 → Rule-based → Human
What goes in a retry budget?
Max retries per step, per run, max time, max cost

Golden Data Set — The Foundation of Eval

Week 3: Make It Measurable
Slide 1 of 4

What is a Golden Dataset?

A curated, hand-verified set of test cases:

{
  "input": "Invoice INV-442 from Acme Corp for $15,000",
  "expected": {
    "vendor": "Acme Corp",
    "invoice_id": "INV-442",
    "amount": 15000,
    "po_match": true
  }
}

Each case has: input, expected output, and edge case tags.

Slide 2 of 4

Building Your Dataset

1. Collect 20 real examples — From your workflow mapping

2. Hand-verify each — A human checks the expected output

3. Cover the edges — 10 happy path, 10 exceptions

4. Tag each case — 'missing_po', 'duplicate', 'over_threshold'

5. Version control it — Track changes over time


20 good cases beat 200 sloppy ones.

Slide 3 of 4

What Makes a Good Test Case?

• Realistic — Based on actual data, not invented

• Specific — Clear input, unambiguous expected output

• Edge-conscious — Tests both success and failure modes

• Independent — Each case stands alone

• Measurable — Pass/fail is unambiguous


If two people disagree on the answer, it's not a good test case.

Slide 4 of 4

Using Your Dataset

The golden dataset drives everything:

1. Baseline — Run your agent, get a score

2. Improve — Fix the biggest failure patterns

3. Re-run — Score should go up

4. Regression — New version shouldn't break old cases

5. Report — 'Week 3: 85% accuracy, up from 72%'


Without a dataset, you're guessing.

When to Use Frontier

Use frontier models ONLY when:

Pitch to Real Businesses

Week 4: Defend the System
Slide 1 of 4

Why Real Pitches?

Pitching in your head is fiction. Pitching to real people is reality:

• You'll discover objections you never anticipated

• You'll learn what actually resonates

• You'll get feedback on your pricing

• You'll build confidence through repetition

• You might even get a client


Nothing replaces real conversations.

Slide 2 of 4

Where to Find Prospects

1. Your network — Friends who run businesses, former colleagues

2. Local businesses — Walk into a shop, office, or restaurant

3. Online communities — LinkedIn, X, Reddit, Indie Hackers

4. Warm intros — 'Do you know anyone who struggles with X?'

5. Cold outreach — Email or DM with a specific, low-risk offer


Start with warm. Work to cold.

Slide 3 of 4

The Outreach Message

Hi [Name],

I've been building AI agents that automate [specific workflow].

I'm looking for feedback from real businesses — would you be open
to a 15-min call where I show you what I've built and get your thoughts?

No cost, no commitment. Just your honest opinion.

Thanks,
Kevin

Low pressure, high curiosity. Most people will say yes.

Slide 4 of 4

The Feedback Loop

After each pitch, document:

1. What objections did they raise?

2. What resonated most?

3. What did they misunderstand?

4. What would they pay for this?

5. What would they change?


Patterns emerge after 3-5 pitches. That's your market telling you what to build.
